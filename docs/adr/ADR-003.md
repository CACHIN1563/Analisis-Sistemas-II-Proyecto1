# ADR-003: Estrategia de cálculo de intereses y mora

| **Campo** | **Contenido** |
|-----------|---------------|
| **Título** | ADR-003: Uso de patrón Strategy para el cálculo de intereses y mora, con parámetros versionados |
| **Estado** | Aceptada |
| **Fecha** | 25/08/2026 |
| **Contexto** | El sistema debe calcular el plan de amortización (método francés), el interés moratorio y la clasificación de mora. Las tasas, bases de conteo y políticas de mora pueden cambiar por decisión del comité o por regulación. El Código Civil de Guatemala (Decreto-Ley 106) prohíbe el anatocismo (interés sobre interés), por lo que el moratorio debe calcularse solo sobre el capital en mora (sección 6.5). Además, los créditos deben calcularse con la política vigente en su fecha de otorgamiento, no con la actual (sección 6.3.1). El sistema debe soportar múltiples métodos de interés (francés, sobre saldos, fijo) aunque inicialmente solo se use francés. |
| **Decisión** | Se aplica el **patrón Strategy (GoF)** para los siguientes comportamientos:<br/><br/>1. **Método de amortización:** interfaz MetodoAmortizacion con método calcularPlan(capital, tasa, n, fechaInicio). Implementación concreta AmortizacionFrancesa que ajusta la última cuota (sección 6.4).<br/>2. **Cálculo de interés moratorio:** interfaz CalculadoraMoratorio con método calcular(capitalEnMora, tasaMoratoriaDiaria, diasAtraso). Implementación que aplica la prohibición de anatocismo.<br/>3. **Clasificación de tramos de mora:** interfaz ClasificadorTramos con método clasificar(diasAtraso). Implementación que retorna 'Mora1' | 'Mora2' | 'Mora3' | 'Vencido' | 'Vigente' según los rangos (sección 6.5).<br/><br/>Además, las **políticas son parámetros versionados** (objeto PoliticaCrediticia) que incluyen: TNA, base de conteo, tasa moratoria, tramos de mora, política de adelanto (capital vs. cuotas futuras). Cada crédito almacena el idPolitica vigente en su fecha de desembolso.<br/><br/>**Alternativas consideradas:** <br/>1. Funciones fijas con constantes literales. Se descarta porque cualquier cambio en la tasa o en los tramos obligaría a modificar el código y recompilar.<br/>2. Tablas en base de datos sin encapsular en objeto de política. Se descarta porque no permite versionar fácilmente ni pasar la política como parámetro al cálculo.<br/><br/>**Justificación:** <br/>- Cumple el principio OCP (abierto a extensión, cerrado a modificación).<br/>- Permite cambiar de método de interés sin tocar el motor de cálculo.<br/>- La fecha de otorgamiento determina la política, evitando recalcular créditos antiguos con tasas nuevas.<br/>- Las pruebas unitarias pueden inyectar políticas fijas (ej: el caso de referencia 6.4.1). |
| **Consecuencias** | **Positivas:** <br/>- Flexibilidad para cambios regulatorios y de negocio.<br/>- Trazabilidad: cada crédito sabe con qué política se calculó.<br/>- Fácil añadir nuevos métodos de amortización en el futuro.<br/><br/>**Negativas:** <br/>- Mayor número de clases y configuraciones.<br/>- La política debe almacenarse en algún repositorio y ser consultada por el crédito.<br/><br/>**Compromiso asumido:** Se acepta la complejidad adicional de versionar políticas porque es esencial para la auditabilidad y para cumplir con la regulación guatemalteca (sección 6.3.1). Se recomienda almacenar las políticas como JSON en un repositorio o en la base de datos con su fecha de vigencia. |
