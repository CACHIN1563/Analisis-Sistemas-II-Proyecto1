# ADR-005: Implementación de Política de Mora Escalonada mediante Patrón Strategy

| **Campo** | **Contenido** |
|-----------|---------------|
| **Título** | ADR-005: Sustitución de política de mora mediante Patrón Strategy (Cumplimiento OCP) |
| **Estado** | Aceptada |
| **Fecha** | 2026-09-24 |
| **Contexto** | El Proyecto 1 operaba con una tasa moratoria plana del 24% anual. Con los nuevos requerimientos (Proyecto 2), se exige implementar una política de mora escalonada que aumenta la tasa dependiendo de los tramos de atraso (18% hasta 30 días, 24% hasta 60 días, etc.), incluyendo además un recargo de gestión de cobranza (Q25.00) al superar los 30 días. El reto principal es incorporar esta nueva lógica sin alterar el motor de cálculo matemático heredado (`calculadora-mora.ts`) para cumplir con el principio OCP (Abierto/Cerrado). |
| **Decisión** | Se decidió aplicar el **Patrón Strategy** de la siguiente manera: <br/>1. Extraer la lógica comercial a una interfaz `IPoliticaMora`.<br/>2. Crear implementaciones separadas (`PoliticaPlana`, `PoliticaEscalonada`).<br/>3. Computar una tasa efectiva en `PoliticaEscalonada` para hacer una única llamada a `CalculadoraMora` y evitar redondeos prematuros de punto flotante.<br/>4. Centralizar la decisión de qué política inyectar usando una fábrica o catálogo condicionado por la fecha del crédito. |
| **Consecuencias** | **Positivas:** <br/>- Se respeta estrictamente el OCP; la matemática central del Proyecto 1 sigue intacta.<br/>- Sustituibilidad perfecta (LSP): las políticas pueden intercambiarse de forma determinista.<br/>- El código cumple con las reglas de negocio sin introducir condicionales masivos ni clases gigantes (SRP).<br/><br/>**Negativas:** <br/>- Creación de múltiples archivos adicionales que dispersan la lógica comercial.<br/>- Ligeramente mayor complejidad cognitiva para entender de dónde proviene el cálculo exacto de la tasa moratoria. |
